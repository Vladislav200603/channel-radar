# ADR-001: Render + Neon, зовнішній trigger і збір у живому web-процесі

- Статус: прийнято
- Дата: 2026-09-16

## Контекст

Потрібен живий сервіс за три дні, без платного хостингу, для приблизно десяти каналів.
Render web instances засинають, а native Render Cron уже платний. Файлова SQLite на
Render ephemeral disk не є допустимою production БД.

## Рішення

Один FastAPI/Jinja process розміщується на Render Free, PostgreSQL — у Neon Free.
GitHub Actions двічі на годину викликає захищений `POST /internal/collect-all`.
Його `schedule` може суттєво запізнюватися, тому один web-процес також запускає легкий
async scheduler: перевірка при старті та кожні 30 хвилин, поки instance працює.
Канали зі спробою збору менш ніж 25 хвилин тому пропускаються; одночасно збираються
не більш як три канали, один цикл обмежений трьома хвилинами. Startup і GitHub-trigger
використовують спільний lock на весь цикл; після очікування повторно перевіряють, які
канали ще потребують збору. Ручний, зовнішній і внутрішній збір також використовують
ті самі per-channel locks.

Першу невдалу спробу без жодного успішного збору scheduler повторює не частіше ніж
раз на шість годин: опечатка не витрачає ресурси кожні пів години, але тимчасовий
network failure не залишає справжній канал забутим назавжди. Ручний retry доступний
одразу. Канали, які раніше успішно збиралися, повторюються зі звичайним інтервалом.

У локальному режимі scheduler за замовчуванням вимкнений, щоб тести й запуск для
перегляду коду самі не зверталися до Telegram. Production вмикає його через
`SCHEDULER_ENABLED=true` у Docker/Render конфігурації. Shutdown скасовує фонову задачу;
незавершена спроба знову стає доступною для збору після звичайного інтервалу retry.

## Наслідки

- один deployable і немає frontend build/worker/queue;
- GitHub trigger будить sleeping instance і запускає ingestion;
- startup catch-up і внутрішній scheduler зменшують залежність від затримок GitHub,
  поки користувачі тримають сервіс активним;
- cold start видимий першому користувачу;
- точні 30-хвилинні інтервали не гарантовані: сплячий Render instance не виконує
  Python-код, а GitHub може затримати trigger. Цей scheduler не є способом обійти sleep;
- workflow відрізняє доступний канал з активним backfill від помилки, показує warning
  для окремих невдалих спроб і падає, якщо після збору немає жодного доступного каналу,
  але є помилки. Відповідь також містить збережені `source_healthy` / `source_errors`:
  невдалий startup-цикл не приховується порожнім списком наступного cron-збору. Окремий
  помилковий username не робить job невдалим, якщо інші джерела залишаються доступними;
- HTTP-trigger має deadline три хвилини; workflow залишає до чотирьох хвилин на запит
  разом із cold start та дозволяє один retry. Обидві спроби вкладаються у 10-хвилинний job;
- одночасно запускається один web process; для кількох workers знадобився б
  розподілений lock або окремий scheduler;
- при зростанні понад десять каналів collect-all слід винести в worker/queue.

## Відхилені альтернативи

- Render Postgres: короткий життєвий цикл free database;
- Fly.io: немає постійного free tier;
- Cloud Run: для активації потрібен billing account;
- SPA + окремий API: зайва deployment surface для цього MVP.
